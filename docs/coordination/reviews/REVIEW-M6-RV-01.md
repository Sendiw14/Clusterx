## Answers to the handoff's "For the Opus security review" items

1. Origin and cookie only, no CSRF token, on the upgrade: **accepted** (area 4). The in-memory cap of 5 has a race (RV6-08), and the dial leaks sockets (RV6-03). The `didWebSocketSetup` takeover is acceptable with a guard (RV6-10).
2. One master key deriving the encryption and CSRF keys: **accepted** (HMAC label separation). There is no rotation, and `cxs_` should be dropped or the ADR amended (RV6-07). Cookie `exp` equal to Go's absolute expiry is fine. Go enforces idle expiry.
3. CSRF token in HTML and `/bff/session`: **accepted** (area 4).
4. The proxy forwarding any `/api/v1/*` except sessions and stream: the deny-list does not hold against `%2F` (**RV6-01**), and the body cap buffers first (**RV6-02**). Header forwarding, passthrough and the 401/502 mapping are correct.
5. OAuth callback: **correct** (area 1).
6. Logging: **verified** clean (area 7).
7. `'unsafe-inline'`: not exploitable today. Move to a nonce for the console before release (RV6-09).
8. Mock OAuth only in the harness (`playwright.config.ts` and `e2e/stack` only; production refuses endpoint overrides, per `config.ts:65` and its unit test). Login not revoking the previous session is **confirmed** (RV6-06).

## NOT RUN

- Production mode live (`CLUSTERX_ENV=production`, https origin, `__Host-`/Secure cookies in a browser), TLS on browser to BFF and BFF to Go, and real GitHub. Production cookie attributes were checked only at the function level (`cfgprobe.mjs`).
- Process crash through an unhandled `error` on a leaked upstream socket (RV6-03). This was not forced. It needs a Go frame that `ws` rejects.
- Memory exhaustion to the point of OOM (RV6-02). I measured one 400 MiB request only.
- Idle and absolute expiry by elapsed time, Firefox and WebKit, real-browser CSWSH from a second origin (covered by Origin checks in the live spec using a request client).

## M6-exit verdict

**PASS (conditional).** The BFF meets the M6 exit criteria for permission and security paths: OAuth with PKCE and state, sealed `__Host-` cookies, closed-claim EdDSA assertions, Origin plus CSRF on every mutation, Origin-checked WebSocket with revalidation and reconnect-after-logout denial in Go, no secrets in logs or the bundle, and demo isolation. The live suite exercises these against the real stack. No P0 or P1 was found.

Conditions (do not block M6 exit, but must be fixed and re-verified by an independent reviewer before the M8 security and load gate): **RV6-01** (encoded-slash proxy bypass), **RV6-02** (body buffered before the cap) and **RV6-03** (upstream socket leak). **RV6-09** (nonce CSP) must be fixed or formally accepted by the owner before release. P3 items RV6-04..08 and RV6-10 are recommended in the same fix ticket. RV6-07 needs the contract owner to amend ADR-0006 §3 text.

### Recommended ADR-0006 wording on the role claim (contract owner, Opus)

My finding: Go never authorizes from the assertion's `role`. `authenticate` (`internal/api/auth.go:53-71`) builds the principal from `sess.Role`, which comes from `users.role` and is joined fresh from PostgreSQL on every request (`store/sessions.go:56`, no cache). The claim only triggers an audit row. Probes I and J prove this live in both directions: a stale operator hint after demotion and a forged operator hint on a viewer both get 403. The BFF's role source is the Go `POST /sessions` response at login. It is never refreshed, but it is never authoritative either.

Proposed text:
- **§1 table, `role` row:** "Hint only, never authoritative. Go authorizes every request from `users.role` read in the same PostgreSQL session lookup (no cache), so a role change takes effect on the next request without re-login. The claim can neither grant nor restrict access. A mismatch writes security audit `assertion.role_mismatch` (`claimed`, `effective`, `kid`)."
- **§2, replace "The BFF then refreshes the session's effective role (see §5)":** "The console always displays the role from `GET /me`, never the cookie. When `/me` returns a role that differs from the sealed hint, the BFF re-seals the cookie with the `/me` role [or: clears the cookie and requires re-login], so `assertion.role_mismatch` fires at most once per role change and session." Pick the option the implementation follows (RV6B-02). If the backend dedupes or revokes instead, state that.
- **§3 cookie bullet, append:** "`role` and `login` in the envelope are display and assertion hints, not access decisions. During a key rotation, CSRF tokens derived from the previous key also verify. The BFF always issues tokens from the current key."
